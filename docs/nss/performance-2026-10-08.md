# 2026-10-08 Redmi AX3000 吞吐与 CPU 实测

## 测试条件

真机为 Redmi AX3000 / IPQ5018 / 256 MiB，Linux 6.12.108，NSS 12.2，
`wifi_only=1`、`nss_offload=1`、`frame_mode=2`。重点测试 **5 GHz AX / HE160，
主信道 36，中心频率 5250 MHz**；路由器和电脑均确认实际使用 160 MHz，
DFS CAC 完成后才开始传输。

电脑千兆有线网卡和双流 Wi-Fi 网卡分别作为端点。Wi-Fi 网卡放入独立网络
命名空间，避免同机地址被本地路由短路；两个方向分别运行 iperf3 客户端，
另一端作为服务器。电脑互联网经手机 USB，共享网络不参与本地吞吐数据路径。

TCP 单流和四流各测 30 秒，另跳过前 3 秒预热；数值为接收端有效吞吐。
UDP 使用 1200 字节负载，发送速率为本轮最低 TCP 吞吐的约 70%。
持续负载为 600 秒双向 TCP、每方向两流，并发每秒 5 次 ICMP。
路由器约每秒采集一次 `/proc/stat`，按传输时间窗口计算每核 busy，包含 softirq。

这些 LAN↔Wi-Fi 测试包含 Linux bridge / DSA host 路径，不能作为有线端到端
NSS 卸载、纯 Wi-Fi AP↔STA NAT 吞吐或关闭 NSS 的性能对照。

## 吞吐

单位：Mbit/s；上传指 Wi-Fi→LAN，下载指 LAN→Wi-Fi。

| 无线模式与配置 | TCP 单流上传 / 下载 | TCP 四流上传 / 下载 |
|---|---:|---:|
| 2.4 GHz HE40，信道 11，优化前 | 156.38 / 56.92 | 136.18 / 47.31 |
| 5 GHz HE80，信道 149，优化前 | 356.69 / 585.71 | 336.67 / 534.88 |
| 5 GHz HE160，信道 36，优化前 | 449.32 / 634.52 | 458.93 / 636.23 |
| HE160，仅启用 Linux packet steering | 571.68 / 910.08 | 580.84 / 888.17 |
| HE160，最新完整固件、Linux steering＋NSS 双 host RX 队列 | 544.15 / 912.94 | 563.08 / 909.41 |

Linux steering 已带来大部分下行提升。手工双队列测试的上传会随连接元组和
负载分配波动，不能把其中一次峰值当成固定收益。没有以关闭 NSS 的 host
路径作为基准，该路径既有接收故障仍需单独验证。

最新固件在两个方向分别进行的 380 Mbit/s 单向 UDP 测试中，上传丢包 0%，下载丢包
0.00514%。600 秒双向 TCP 为 **272.33 / 529.57 Mbit/s**，合计 801.90 Mbit/s。

## 5 GHz HE160 CPU、内存和持续负载

| 最新固件测试 | CPU 0 平均 busy | CPU 1 平均 busy | 最高温度 |
|---|---:|---:|---:|
| TCP 单流上传 | 98.20% | 40.70% | 61°C |
| TCP 单流下载 | 96.91% | 83.30% | 61°C |
| TCP 四流上传 | 99.34% | 44.81% | 63°C |
| TCP 四流下载 | 97.32% | 90.60% | 62°C |
| 600 秒双向 TCP | 98.85% | 82.85% | 73°C |

600 秒负载窗口的 CPU 采样覆盖 599.67 秒；该窗口最小 MemAvailable 为
12068 KiB，采样中的 CPU 频率为 1008 MHz；温度列取各温度传感器最大值。
CPU 0 已接近处理上限，双向测试不能只看两核平均值。

该 600 秒窗口没有发现固件崩溃、重启或无线断连，但并发 ICMP 丢包
**19.739%（2989 发、2399 收）**，平均 RTT 16.683 ms。随后空闲状态同样
每秒 5 次 ICMP 为 105 发、105 收。NSS N2H 优先级队列 drop 计数有增长，
满载丢包尚未解决，不能把这一轮标为完整稳定性验收通过。

`n2h_rx_queue[0..3]_drops` 是四个固件优先级队列的计数，不能直接映射为
CPU 0/1 的两个 host RX 队列。不同启动的累计计数也不能直接相减。
HE80 的持续测试约 212 秒时为优先测 HE160 而主动中止，不作为 600 秒通过记录。

随后 60 秒满载定位中，两个端点抓包均无内核捕获丢包：324 个 ICMP 请求有
17 个未到达有线端，有线端对收到的 307 个请求全部回复，其中 12 个回复未
到达无线端。这将丢包范围缩小到两个物理端点之间，而非有线端没有作答。
该轮双向 TCP 为 401.56 / 343.01 Mbit/s，两核平均 busy 为 96.91% / 95.36%。

固定相同 TCP 数据端口后，将 Ethernet IRQ 和 Linux RX steering 对调到另一核，
双向吞吐降为 365.02 / 186.41 Mbit/s，ICMP 请求丢失 42/174。该组调整没有
收益，已撤销，不写入启动脚本；这两个短测不替代上面的 600 秒主测试。

## 固件优化与验证依据

最新本地镜像版本为 `r0-nssrelay20261008opt2-fe7e690dcd`，SHA256：

```text
a1b9cc955f74684f123b3b9a0f155e2ddf9fe39d63650d91f9140255210b927c
```

Debian 12.15 / GCC 14.3.0 完整构建通过。ath11k release 6、NSS driver
release 24、nss-wifi release 5、ECM release 2 已成套刷入，真机模块哈希与
构建产物一致，内核 ABI 为 `84e3bcac6c4c8f27fcf530e56c9b87d5`。
对实际构建源码执行的 17 组无线测试与 15 组中继测试全部通过；这属于源码
和错误路径验证，不代替真机吞吐与重连测试。

- NSS 开机配置两个 host RX 队列，分别绑定 CPU 0/1；Linux packet steering
  在本次保留的设备配置中设为 1。IRQ 计数确认第二队列实际收包。
- 修正 NSS RPS sysctl 的状态回滚、失败返回值和 priority map 输入长度。
  固件不支持运行中关闭 RPS，写 0 现在明确拒绝并保留真实的启用状态。
- 严格校验 NSS 接收速率样本。真机曾上报双流设备的 `nss=5`，无效样本
  保留上一条有效速率；这是显示统计修复，不能解释实际握手丢帧。
- ECM 使用 256 MiB profile 的较小哈希桶表。实测 ECM VMALLOC 从
  2007040 降至 102400 字节，减少 1904640 字节，约 1.82 MiB；不裁剪连接功能。

原始 iperf JSON、CPU 采样、ping 和状态记录保存在桌面刷机备份的
`throughput/` 目录。主要文件为 `suite-results.jsonl`、
`cpu-5g-he160-optimized.json`、`router-optimized-he160-cpu-1s.log` 和
`5g-he160-optimized-soak-ping.log`。

## 上联恢复与后续验证边界

角色对调后恢复原 AP＋STA 布局，曾重现 5 GHz WPA 四次握手超时。
限制单 host 队列、关闭 Linux steering，以及重启后完全关闭原生 NSS RPS，
均未消除这一轮故障。电脑以自身和路由器测试 MAC 连接同一上游均认证成功；
随后路由器上联恢复，重新开启双队列仍可联网。最终软件重启又复现该故障，
暂停 STA 15 秒也未恢复；再次完成电脑同 MAC 对照后，路由器认证和 DHCP 恢复。
该过程尚未确认根因，不能视为已经修复重启恢复，
不将普通版本也出现过的共性故障归因于 NSS 双队列。

恢复后的 2.4 GHz AP＋5 GHz STA 完成限量公网下载，路由确认经无线回程，
NSS IPv4 special 转发包由 307 增至 31777，转发字节增量约 41.8 MB。
这证明该次下载窗口有实际 NSS 转发，不将公网限速下载作为回程峰值测速。

最终保留原布局：2.4 GHz HE40 / 信道 11 AP＋5 GHz VHT80 / 信道 149 STA。
无线配置文件与最初备份的 SHA256 一致，`wwan.metric=0`、`wan.metric=100`，
路由确认优先走 Wi-Fi。恢复后路由器和无线客户端访问公网各 5 次均无丢包；
移除电脑测速端点后，路由器再次 5/5 无丢包。电脑继续经手机 USB 联网。

仍需关注满载 ICMP 丢包、反复角色切换后的 WPA 恢复，以及 host RX 回退。
IPv6 上联、透明 WDS、DSA Ethernet NSS 接管和完整组播同步未在本轮验收。
